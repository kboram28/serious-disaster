GPT 기반 중대재해 유형 분류 시스템

산업현장 중대재해 사례를 근거로 재해유형 분류, 유사 사례 검색, 예방대책, 사고 발생 시 대응을 안내하는 챗봇. 유실된 졸업작품(V1)을 다시 만들면서 데이터와 구조를 개선하고(V2.2), 두 버전을 같은 조건에서 비교했다.

04진행 과정

  1. 준비가상환경, API 키, git, SIF API 활용신청
  2. 엑셀 정제와 라벨 재검증시도 표기 42종 → 17종, 라벨 오류 63건(12.4%) 발견, 분류 기준 확정
  3. V1 재현과 평가 설계사례 전체를 프롬프트에 넣는 방식으로 재현, 테스트 100건 분리, 블라인드 정답, 질문 43개
  4. SIF 수집공공데이터 오픈 API로 6,032건 (호출 61회)
  5. V2 구축SIF 유형 분류(원래 유형과 일치 90.6%), 엑셀 기인물·원인 추출, 통합 6,441건, 검색 엔진
  6. 비교 평가와 개선V1 vs V2 → 사고대응 약점 발견 → V2.1 → 새 질문으로 검증 → V2.2 확정
  7. 웹 화면챗봇(사진 입력), 사고 데이터 분석, 자주 묻는 질문, 통계·사례 검색

06공정한 비교를 위한 장치

  • V1·V2 같은 모델: 차이를 데이터와 구조로만 해석
  • 테스트 100건을 어느 DB에도 넣지 않음: 정답 사례를 그대로 찾아 점수가 부풀려지는 것 방지
  • 블라인드 라벨링: GPT 판정을 보고 검수하면 GPT 쪽으로 기우는 것(앵커링)을 1단계에서 확인했기 때문
  • 답변 비교는 A/B 순서를 섞어서, 사람 채점이 끝난 뒤 GPT 채점 공개
  • V2.1은 고치기 전에 정한 새 질문으로 검증 (과적합 방지)
  • 사람과 GPT 채점 일치율 44%·67% → 사람 채점과 자동 검사를 주 근거로 사용

07한계와 향후 과제

  • 사고대응의 "지금 바로 할 일"은 GPT의 일반 응급조치 지식이다 → KOSHA GUIDE 연결 (활용신청 완료, 미진행)
  • SIF는 장소가 익명화되어 지역 검색은 공단 재해사례(6%)에만 가능
  • SIF 6,032건의 유형은 GPT 판정이며 사람 검수는 하지 않음
  • 사람 채점 규모가 작음 (16 + 15문항), 사진 기능은 정량 평가하지 않음

08질문 받았을 때

한 줄
"졸업작품에서 데이터 수집·정리와 웹 제작을 맡았고, 다시 구축하면서 데이터 품질 문제를 찾아 분류 기준을 세우고, 개선 전후를 공정하게 비교하는 평가를 설계·수행했습니다."
30초
"졸업작품에서 저는 안전보건공단 재해사례를 수집해 정리하고 웹 화면을 만들었습니다. 코드가 유실되어 다시 만들면서 개선을 목표로 했는데, 기존 데이터의 재해유형 라벨 12%가 잘못되어 있었습니다. 그래서 매몰과 깔림을 구분하는 것 같은 분류 기준을 직접 정하고 데이터를 검수했고, 공공데이터 API로 사례를 6천 건 이상 추가해 검색 기반 구조로 바꿨습니다. 블라인드 평가로 분류 정확도 93%에서 97%, 비용은 15분의 1로 줄어든 것을 확인했습니다. 구현에는 AI 코딩 도구를 활용했고, 저는 방향 결정과 데이터 검수, 평가를 맡았습니다."
AI가 코드를 짰으면 본인이 한 건 뭐예요?

어떤 데이터를 쓸지, 무엇을 정답으로 볼지, 어떻게 공정하게 비교할지는 제가 정했습니다. 토사 매몰을 깔림으로 볼지 기타로 볼지는 구조 방법과 예방대책이 다르다는 이유로 구분하기로 했고, GPT 판정을 미리 보면 판단이 기운다는 걸 확인한 뒤로는 블라인드 라벨링으로 바꿨습니다.

가장 어려웠던 점은?

분류 기준이 문서로 없었던 점입니다. '떨어진 뒤 슬라브에 깔림'처럼 두 가지가 겹치는 사례가 계속 나와서, 사람이 입은 피해의 가장 큰 원인으로 판단한다는 원칙을 세우고 예외를 하나씩 기록했습니다.

결과가 기대보다 안 좋았던 부분은?

답변 품질은 사람 평가에서 8대 6으로 차이가 크지 않았고, 사고대응 질문은 예전 버전이 낫다는 평가가 나왔습니다. 응급 상황에서는 할 일을 먼저 보여주는 형식으로 바꾸고, 새 질문으로 다시 평가해 5대 0으로 개선을 확인했습니다.

왜 크롤링 대신 API를 썼나요?

이용 조건이 명확하고, 사이트 화면 구조가 바뀌어도 수집 코드가 깨지지 않으며, 기인물·재해유발요인·감소대책이 구조화된 필드로 제공되기 때문입니다.

벡터 DB는 뭘 썼나요?

별도 벡터 DB는 쓰지 않았습니다. 사례가 6,441건이라 OpenAI 임베딩을 numpy 배열로 저장하고 전체와 코사인 유사도를 계산해도 수 밀리초면 충분했고, 설치와 운영이 단순해서입니다. 사례가 수십만 건으로 늘면 FAISS나 Chroma 같은 벡터 DB로 바꿀 계획입니다.

GPT 채점은 믿을 만한가요?

사람 채점과의 일치율이 44%와 67%로 높지 않았습니다. 그래서 GPT 채점은 참고로만 쓰고, 조건 준수 같은 자동 검사와 사람 블라인드 채점을 주 근거로 썼습니다.

팀원 김세진의 역할은 직접 채워 넣을 것.
